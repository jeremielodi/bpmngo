# Benchmark audit — BpmnGo vs Camunda 8.10.7

Date: 2026-11-04 · Machine: Windows + Docker Desktop, 12 vCPUs, Go 1.27.1, Node 24.15
Engines: BpmnGo 1.0.4 (built from `main` at `4b30366`), Camunda 8.10.7 (`camunda/camunda:8.10.7`)
Both: **2 dedicated vCPUs, 2 GiB** — Camunda `cpuset=2,4` / `mem_limit=2g`; BpmnGo `cpuset=6,8`, app 1 GiB + PostgreSQL 1 GiB.
Camunda: `CAMUNDA_CLUSTER_PARTITIONCOUNT=2`, connectors stopped, H2 secondary storage (distribution default).

This run answers two questions: *is the benchmark fair?* and *is BpmnGo actually faster than Camunda 8?*

---

## 1. Verdict

**Yes — on this workload and this hardware, BpmnGo wins every performance metric. But the
published margin is overstated, and two of the published numbers do not mean what they look like.**

| Metric | Camunda 8.10.7 | BpmnGo 1.0.4 | Ratio |
|---|---|---|---|
| Highest fixed rate sustained (no refusal, p99 ≤ 1 s) | 10 inst/s | 30 inst/s | **3.0×** |
| Highest rate observed before collapse | ~14.8 inst/s | ~44 inst/s (extrapolated from 182 % CPU at 40) | **3.0×** |
| Closed-loop throughput, 50 clients | 19.1 inst/s | 45.8 inst/s | **2.4×** |
| Closed-loop throughput, 100 clients | 19.7 inst/s | 45.0 inst/s | **2.3×** |
| p50 end-to-end, at 10 inst/s offered | 202 ms | 39 ms | **5.2×** |
| CPU per finished instance (steady state) | 47–60 ms | 39–45 ms | **1.25–1.4×** |
| Memory peak under load | 650–767 MiB | 430–640 MiB | **1.2–1.8×** |
| Memory idle | ~514 MiB | ~85–170 MiB | 3–6× |
| `CreateProcessInstanceWithResult` p50 (warm, no load) | 34–47 ms | 16–17 ms | **2.2–2.7×** |
| `CreateProcessInstance` p50 | 30–35 ms | 14–15 ms | **2.2×** |
| Creation → job p50 | 53–62 ms | 19–20 ms | **2.8–3.1×** |
| `CompleteJob` p50 | 19–23 ms | 14–15 ms | 1.4× |
| `DeployResource` p50 | 27–37 ms | 16–18 ms | 1.8× |
| `Topology` p50 | 2.2 ms | 1.6–1.9 ms | 1.2× |

Two corrections to the README's framing:

1. **The 0.27× CPU and 0.22× memory figures come from the behaviour suite, not from load.**
   Those 87 scenarios spend most of their time waiting on real timers; BpmnGo idles at 9 % CPU
   there against Camunda's 27 %, which is mostly JVM + Operate/Tasklist + H2 exporter baseline.
   That is a **footprint** number. Per *instance processed*, the difference is 1.25–1.4×, not 3.7×.
2. **The throughput win is not "the engine is 3× more efficient" — it is that Camunda does not use
   its second core.** Camunda hits its request limiter at ~14–15 inst/s while burning 84–89 % of
   *one* core of the two it has. BpmnGo fills both cores (182 % at 40 inst/s).

Both engines were run from the same client code, same proto, same workload, same worker pool:
the comparison itself is sound. I also tested the one configuration suspicion that could have
explained the gap — Camunda was running on a 512 MiB JVM heap out of its 2 GiB. Giving it 1.40 GiB
and thread counts matched to 2 cores moved throughput from 22.8 to 23.3 inst/s at 25 offered, so
the gap is **not** memory starvation (§4.10).

**Where each engine breaks:**

- **Camunda** stops *accepting* work at ~14–15 inst/s. It returns `RESOURCE_EXHAUSTED` (Zeebe AIMD
  request limiter) with a whole core still free. Latency of what it does accept is ~1–2 s.
- **BpmnGo** never refuses. It queues: at 50 inst/s offered it completes 50/s but the p50 end-to-end
  is **12.8 s**. Past ~45 inst/s (both cores pegged) it degrades into *incidents*:
  `⚠️ incident on end (instance …): failed to commit transaction: timeout: context deadline exceeded`
  (`docker logs bpmngo-app`). 13–49 `INTERNAL` gRPC errors per level above 100 inst/s offered.

## 3. What the existing benchmark gets right

- **The comparison is reproducible and not cherry-picked.** Re-running
  `npm run compare -- --compare reference-camunda-8.10.7/traces/camunda results/final2-20261103-0937/traces/bpmngo`
  gives exactly `Scenarios: 87 same: 87 expected: 0 different: 0 missing: 0` from the committed traces.
- **It compares what a client can observe**, section by section, with canonical JSON (`src/compare.ts`),
  not a fuzzy pass/fail. Jobs of parallel branches are compared sorted (`unordered`), error wording
  and timings are excluded (`src/compare.ts:31`).
- **Both engines are driven by the same code**: official `gateway.proto`, gRPC + `/v2`
  (`src/engine.ts`), and the same worker pool (`src/load.ts:140-157`).
- **Capacity was equalised** (2 cores / 2 GiB each) and the report prints each container's limits,
  so an un-equalised run is visible (`src/resources.ts:85-95`).
- **CPU time is exact** — cgroup `usage_usec` delta, not `docker stats` sampling (`src/resources.ts:70-82`).
- **Camunda's 2 partitions** are applied (`limits/camunda-2p.yaml`); with the default single partition
  it would use one core only.

## 4. What it overstates or leaves out

### 4.1 The rate ladder never reaches either engine's ceiling

The published load run stopped at **15 inst/s** (`results/load-2026-11-03T01-11-18/`), where
BpmnGo used **101 %** of its 200 % and Camunda **79 %**. Neither engine was saturated, so
"15 vs 5 inst/s" measures where Camunda's *admission control* starts, not where either engine
runs out of capacity. Measured here, the real knees are **30–40 inst/s (BpmnGo)** and
**10–15 inst/s (Camunda)**. The README's example ladder is `--rates 5,10,15,20,25`; it needs to go
until both engines break.

### 4.2 "Highest fixed rate sustained" measures admission control, not capacity

`sustained()` (`src/load.ts:287-288`) requires zero refusals, ≥98 % completion and p99 ≤ 1 s.
- Camunda **refuses** (`RESOURCE_EXHAUSTED`) while half-idle — punished.
- BpmnGo **never refuses** and lets latency grow — rewarded until p99 crosses 1 s (at 30 inst/s),
  then, past ~45 inst/s, it converts overload into *incidents* instead of back-pressure.

So the column is "the rate at which this engine still looks good", not "the rate it can do". Both
numbers should be published, and the failure mode named.

### 4.3 The first level of every run is contaminated by cold start

`cpuMsPerInstance` (`src/load.ts:275`) and the CPU columns for level #1 include JVM warm-up:
published `camunda 262.6 ms/inst` at 5 inst/s vs `55.1 ms` at 15 inst/s — CPU time per instance
*dropping 4.8×* while the rate triples is only possible if level #1 was cold. My own run reproduced
it (143.4 vs 48.9 ms). **Fix:** add a separate warm-up phase before level #1 (`--warmup` currently
warms inside level #1), or exclude level #1 from the CPU columns.

### 4.4 The headline CPU/memory ratios are from the behaviour suite

`README.md:48-49` — "0.27× Camunda's CPU time and 0.22× its peak memory, ran it in 0.81× the time".
That is the 87-scenario run, ~5 minutes per engine, dominated by real timers and 2–4 s waits.
It measures **idle footprint**, not efficiency: BpmnGo idles at 9 % CPU, Camunda at 27 % (JVM +
Operate/Tasklist + H2 exporter). Under load the per-instance difference is 39–45 ms vs 47–60 ms.
The ratio is true but it is answering a different question; it should be labelled "deployment
footprint", and the throughput claim should cite the load numbers.

### 4.5 Camunda is measured in its lightweight H2 distribution

`benchmark/camunda-8.10.7/configuration/application-h2.yaml` sets `cpu-thread-count: "3"` on a
2-vCPU cpuset, and the same container runs the H2 exporter for Operate/Tasklist. That exporter is
a large share of its CPU and is what throttles it at ~14 inst/s while a core sits idle. This is a
legitimate "out of the box" measurement, but the claim must be scoped: **"3× faster than the
docker-compose Camunda 8.10.7 on 2 cores"**, not "3× faster than Camunda 8". A production Camunda
(Elasticsearch/OpenSearch, separate webapps, more partitions) would be much faster than this, and
much bigger than this.

### 4.6 BpmnGo's number excludes Kafka; Camunda's does not

BpmnGo ran `WRITE_PATH=direct`, `EVENT_LOG=off`, no Redpanda — the product default, but it means
BpmnGo is not paying for a replicated log while Camunda always pays for its Raft log. The bench
supports `partitioned` mode; the published figures should say which one they used, and ideally
show both.

### 4.7 Single run, no repeats

`--repeat` defaults to 1 (`src/load.ts:84`); the published load run is a single pass, so there is
no variance. Pass-to-pass swings I measured reach ~25 % (`DeployResource` p95 66.6 vs 49.5 ms).
`README.md:299` shows `--repeat 3`; the numbers should come from it.

### 4.8 Small defects in the harness

- **Division by zero** in the "heaviest statements" table when a level completed nothing:
  `f(q.execMs / last.completed, 3)` (`src/load.ts:358`) printed `Infinity ms  Infinity×` at the
  300 inst/s level.
- **`CLIENT_LIMIT` hides the ceiling**: `MAX_IN_FLIGHT = 2000` (`src/load.ts:59`) plus the 40 s
  start deadline means that at ≥100 inst/s offered the *client* becomes the limiter. Above
  ~45 inst/s the harness cannot say what BpmnGo would do — that is not BpmnGo failing, and the
  report should say so.
- **Pin-to-physical-core cannot be verified on Docker Desktop**: the README's topology check runs
  inside the Linux VM, where `cpuset=6,8` are vCPUs. Both engines got 2 vCPUs, so the comparison
  stays symmetric, but "two physical cores" is not something this host can guarantee.

### 4.9 Throughput counts work that finishes after the window

In rate mode a level ends when the send window closes, but `done` keeps receiving completions during
`await Promise.all(pending)` (`src/load.ts:240-241`), and `throughput = done.length / durationS`
(`src/load.ts:265`). The column is therefore "starts issued in the window that eventually completed,
per second of window" — not "completions per second". For an engine that queues, that inflates the
figure: BpmnGo at 50 inst/s offered reported **50.0 inst/s** while its p50 end-to-end was 12.8 s,
i.e. ~640 instances were still in flight when the window closed. At the knees (p99 ≤ 1 s, no backlog)
the two definitions agree, so the knee conclusions hold; the saturated rows do not.

Related: `started++` runs before the `MAX_IN_FLIGHT` check (`src/load.ts:224-226`), so a start that is
never sent still counts as started and counts against the ≥98 % completion rule.

### 4.10 The JVM heap was the obvious suspect — it is not the cause

The 2 GiB limit is not the 2 GiB Camunda gets to *use*: with no `-Xmx`, `MaxRAMPercentage` defaults to
25 %, so the broker ran on a **512 MiB heap**, while BpmnGo's Go runtime may use most of its 1 GiB.
The budgets were not equal in practice. I tested it with `limits/camunda-tuned.yaml`
(`-XX:MaxRAMPercentage=70` → 1.40 GiB heap, `cpu-thread-count`/`io-thread-count` 2 for 2 cores):

| Offered | Camunda as shipped (512 MiB heap) | Camunda tuned (1.40 GiB heap, 2 threads) |
|---|---|---|
| 10 | 10.0 inst/s, p50 202 ms, CPU 144 % | 10.0 inst/s, p50 396 ms, CPU 182 % |
| 25 | 22.8 inst/s, 207 refused, CPU 112 % | 23.3 inst/s, 154 refused, CPU 145 % |
| 50 | not run | 21.0 inst/s, 2 360 refused, CPU 106 % |

Throughput did not move (23.3 vs 22.8 at 25 offered) and the ceiling stays at ~21–23 inst/s. The gap
is **not** memory starvation: it is the 2-partition stream processor plus the in-container H2 exporter,
with Zeebe's AIMD limiter clamping admission. That strengthens the result — but note the first level
of the tuned run got *worse* (396 ms p50), which is finding 4.3 again: a bigger heap makes the cold
start longer, and the harness measures it.

## 5. What this says about the engine

The measurements point at one bottleneck and one missing feature.

**Bottleneck: PostgreSQL round trips per instance.** For a 4-element process (start → 2 tasks → end),
BpmnGo runs **111–157 SQL statements, 35–47 commits and ~19 KiB of WAL per finished instance**
(`pgstats.ts`, this run). At 40 inst/s that is ~1 600 commits/s, and PostgreSQL consumes ~65 % of
the deployment's CPU against the app's ~35 %. Throughput is bound by commit rate, exactly as
`docs/operations.md:96` says. Cutting the write path to ~10 commits/instance would move the ceiling
much more than any micro-optimisation in the engine.

**Missing: admission control.** Camunda's `RESOURCE_EXHAUSTED` is ugly but safe — it tells the client
to slow down. BpmnGo accepts everything, and past ~45 inst/s turns overload into
`failed to commit transaction: timeout: context deadline exceeded` **incidents** on instances that
were already accepted. For a "production ready" claim, that is the more important gap of the two:
a load spike silently produces incidented instances instead of back-pressure.

## 7. The BPMN models themselves

`benchmark/bpmn/` holds 12 files, 67 processes, used by 82 scenarios (+5 API checks = 87).

**They are good, and they are valid.** Checked mechanically, then empirically:

| Check | Result |
|---|---|
| Well-formed XML | 12/12 |
| `<process isExecutable="true">` | 67/67 |
| `serviceTask` with a `zeebe:taskDefinition type` | 125/125 |
| Duplicate ids / dangling `sourceRef`/`targetRef` | none |
| `BPMNDiagram` (diagram interchange) | 12/12 — these are modeler-shaped files, not bare fixtures |
| Scenario → file → process id → job types | 82/82 match (the 2 "no process" hits are the `.dmn` resource, not a model) |
| Deployed on a real Camunda 8.10.7 | **87/87 `deploy: ok`** in `reference-camunda-8.10.7/` |

The figures above describe the 12 files the suite had before 2026-11-04; §7.1 lists what was
added afterwards and how it was validated.

The models encode engine-specific knowledge rather than being generic: non-interrupting boundaries
use `cancelActivity="false"` (5 of them), event sub-processes use `triggeredByEvent`, and
`tasks_compensation.bpmn` carries the comment *"Camunda 8.10 fails the deploy with an NPE if a
compensateEventDefinition has no id"* with the workaround in place. `gw_exclusive_nodefault` is
deliberately a wrong model (no default flow, no true condition) — that is the scenario, and it is
correctly isolated in its own process.

Element coverage: 125 service tasks, 43 script tasks, 16 boundary events, 13 sub-processes,
12 intermediate catch events, 11 parallel / 9 exclusive / 6 inclusive gateways, 5 multi-instance,
4 call activities, 4 escalations, 2 event-based gateways, 2 compensations, 2 terminate ends,
2 link events, 1 business-rule task with a DMN decision, 3 event sub-processes, 1 user task.

**What they do not cover:**

1. **Size.** 15.8 elements per process on average, 50 at most (`rb_modeler_order`). No realistic
   80–150 element model, so the cost of *parsing and deploying* a large model is never measured —
   even though `DeployResource` is one of the reported calls.
2. **User tasks.** One `userTask` in the whole suite (with `zeebe:userTask` and an assignee, but no
   form, no candidate groups). Tasklist is a large Camunda surface that is essentially untested.
3. **DMN.** One decision with two rules, one hit policy. No multi-table decisions, no date/list types.
4. **Uncovered elements:** conditional start/intermediate events, ad-hoc sub-process, transaction,
   receive/send/manual task.
5. **Concurrency.** Every scenario runs one instance at a time, so ordering and contention between
   correlated messages, signals or parallel branches are only exercised by the load test — and the
   load test uses a 4-element process.

**What to add**, in order of value: a `large.bpmn` (80–120 elements, 20 gateways, nested sub-processes)
used by both `npm run latency` and a load level; a user-task model with a form and candidate groups;
a DMN model with two tables and different hit policies. Those three close the gap between "behaves
like Camunda" and "performs like a real deployment".

### 7.1 Added since (2026-11-04)

| File | What | Scenarios |
|---|---|---|
| `large.bpmn` | 4-way parallel fork inside a sub-process, join, script task, default-branch gateway, sequential multi-instance, nested audit sub-process (~70 elements, 4.4× the 15.8 average) | `large-model-auto-approval`, `large-model-manual-and-second-approver` |
| `usertask_form.bpmn` + `approval.form` | user task with a form, candidate groups and a priority; a second process assigned to one user | `user-task-form-candidate-groups`, `user-task-assigned-to-one-user` |
| `dmn_two_tables.dmn` + `dmn_two.bpmn` | two chained decisions, hit policies FIRST and UNIQUE, the second reading a variable the first produced | `dmn-two-tables-platinum`, `dmn-two-tables-standard` |

All six were run against a live Camunda 8.10.7 and BpmnGo: **6/6 same**. The suite is now 88
scenarios (+5 API checks). `npm run load -- --process bpmn/large.bpmn` puts that model under load
(job types read from the file); a smoke run sustained 9.9 of 10 offered inst/s, p50 269 ms, no errors.

Two things the new models taught, both worth knowing before writing another scenario:

1. **Never share a job type between two parallel branches.** Whether the two jobs arrive in one
   activation batch decides which variables they carry: Camunda snapshots at activation, so the
   second job saw only the start variables, while BpmnGo's second job already carried the
   siblings' results. The trace then differs for a reason that belongs to the harness, not to the
   engine. Each branch now has its own type.
2. **A `zeebe:formDefinition` pointing at a form that is not deployed gives Camunda an incident**
   (`FORM_NOT_FOUND`, task stuck in ACTIVE) while BpmnGo simply completes it. Deploying the form
   fixes it — but only with `schemaVersion: 5`: with `schemaVersion: 1` Camunda accepts the
   deployment and still cannot resolve the form at runtime, which is a quietly misleading failure.
   BpmnGo does not raise the incident either way: it stores the form reference without checking it.
